# 경력기술서 — 심재혁

> 재직 중인 회사의 사명·코드·내부 식별자(테이블명, 엔드포인트 경로 등)는 담지 않았습니다.
> 문제와 해결 방식만 기술합니다.

---

## 요약

해외 상품 소싱 커머스 SaaS의 백엔드를 2021년 2월부터 담당하고 있습니다.
상품 수집기(크롬 확장 + 서버), 오픈마켓 상품 업로드, 주문·물류(배대지), 결제·정산까지
플랫폼의 주요 도메인을 직접 설계·구현·운영했습니다.

- 기간: 2021.02 ~ 재직 중 (5년 7개월)
- 기여: 커밋 3,923건(머지 제외), 수정 파일 3,065개, 연평균 692커밋
- 사용 기술: PHP, MySQL, JavaScript(ES2020+), Chrome Extension MV3, Linux/Cron
- 담당 비중: 상품 소싱·등록 33% / 셀러 UI 18% / 주문·물류 16% / 수집 엔진·확장 14% /
  배치·크론 9% / 결제·정산 5% / 오픈마켓 연동 5%

주로 다룬 문제는 **외부 사이트·외부 API에 의존하는 작업이 조용히 실패하는 것**입니다.
수집이 실패했는데 "완료"로 보이거나, 결제가 등록만 되고 청구가 누락되거나,
큐 슬롯이 반납되지 않아 처리량이 줄어드는 문제들을 반복해서 다뤘고,
그때마다 원인을 재현·계측한 뒤 구조를 바꾸는 방식으로 해결했습니다.

## 1. 수집 완료로 표시되지만 상품이 등록되지 않던 문제

**상황**
셀러들이 "수집이 완료됐다고 나오는데 내 상품 목록에 아무것도 없다"고 반복 문의.
재현이 되지 않아 오랫동안 미해결로 남아 있던 이슈.
수집 실패 로그를 집계해보니 2026년 실패 34건 중 22건(65%)이
`데이터가 없습니다(0001)` 처럼 **원인을 알 수 없는 문구**였습니다.

**원인**
브라우저 확장이 "어느 계정으로 수집할 것인가"를 판단하는 인증 정보의 **저장 조건이
계정과 무관한 부가 데이터에 묶여** 있었습니다. 그 부가 데이터가 없는 계정에서는
갱신 자체가 일어나지 않아 **이전 세션의 값이 그대로 남았고**, 결과적으로 수집 결과가
현재 로그인한 계정이 아닌 곳에 적립됐습니다.
게다가 화면은 서버 상태값을 성공으로 매핑하고 있어 "수집 완료"로 표시됐습니다.
사용자 입장에서는 성공했는데 결과만 없는, 재현 불가능해 보이는 문제였습니다.

**해결**
1. 인증 정보 갱신을 부가 데이터와 분리해, 로그인한 계정을 기준으로 항상 갱신하도록 수정
2. 수집 관련 서버 엔드포인트 여러 곳이 권한 없음일 때 평문 문자열을 반환하던 것을
   `{success:false, msg:"..."}` 구조화 응답으로 통일
3. 확장 공통 모듈에서 서버가 준 사유를 그대로 노출하고, 폴링 실패도 사유가 있는 실패로 확정

**결과**
"완료처럼 보이는 실패"가 사라지고, 셀러가 실패 화면에서 원인을 스스로 확인할 수 있게 됐습니다.
검증은 웹스토어 확장의 서명키를 추출해 로컬 빌드에 주입하고,
Playwright 원격 디버깅으로 실서버 환경을 재현하는 방식으로 진행했습니다.

**되짚어보면**
상태값을 성공으로 매핑한 코드에는 "바꾸면 전 마켓이 배치 완료까지 대기한다"는
의도적 주석이 있었습니다. 증상만 보고 그 매핑을 고쳤다면 더 큰 장애를 만들었을 겁니다.
표시 계층이 아니라 인증 계층이 원인이라는 걸 확인한 뒤에 손댔습니다.

## 2. 특정 쇼핑몰 상세 수집이 로그 없이 실패하던 문제

**상황**
테무(Temu) 상품 수집에서 옵션 데이터만 비어서 들어오는 현상.
에러 로그가 전혀 남지 않아 원인 파악이 어려웠습니다.

**원인**
해당 사이트가 페이지 전역 객체에 **DOM 요소 참조를 넣기 시작**했고,
수집 스크립트의 `JSON.parse(JSON.stringify(...))` 가 순환 참조 에러로 throw.
이 호출이 재시도 블록 안에 있어 10회 재시도가 전부 같은 지점에서 실패하고,
바깥의 빈 `catch {}` 가 에러를 삼켜 로그조차 남지 않았습니다.
결국 결과 메시지가 발신되지 않아 15초 타임아웃으로 조용히 끝났습니다.

**해결**
순환을 유발하는 키가 하나뿐임을 확인하고, **DOM 노드만 걷어내는 replacer** 로 직렬화하도록 변경.
나머지 필드는 형태가 그대로 유지되어 서버 파싱 호환이 깨지지 않았습니다.
추가로 서버 렌더링 원본을 중괄호 매칭으로 잘라 파싱하는 폴백 경로를 뒀습니다.

**결과**
옵션 누락이 해소됐고, 이후 유사 사이트에서도 같은 폴백 전략을 재사용했습니다.

**되짚어보면**
추출식을 옵셔널 체이닝 + 기본값으로 감싸면 편하지만,
**절대 throw하지 않게 되어 빈 객체를 "성공"으로 반환**합니다.
재시도 로직이 있는 코드에서는 실패가 실패로 드러나야 한다는 걸 이 건으로 정리했습니다.

## 3. 수집 큐가 슬롯을 반납하지 않아 처리량이 줄던 문제

**상황**
대량 수집 시 창이 3개까지 열려야 하는데 실제로는 1개만 열려 직렬 처리되고,
느린 상품 하나가 전체 큐를 붙잡는 현상.

**원인** (두 가지가 겹쳐 있었습니다)
1. 워커가 슬롯을 반납하는 시점이 페이지 로드 완료(`complete`) 기준이라,
   실제 창은 아직 떠 있는데 다음 작업이 시작되어 동시 상한이 무의미했습니다.
2. 큐에 URL이 도착하기 전에 워커가 빈 큐를 만나면 종료되는데,
   "처리 중" 플래그가 켜져 있어 워커가 다시 생성되지 않았습니다. → 워커 1개로 수렴.

**해결**
- 슬롯 반납 시점을 **탭이 실제로 닫히는 이벤트**로 변경하고, 닫힘 신호가 없으면 60초 폴백 종료
- 워커 관리를 "플래그로 1회 스폰"에서 **실행 중 워커 수를 세어 상한까지 채우는 방식**으로 교체
  (작업 투입·종료 시마다 부족분을 보충)

**결과**
설정상 3건이던 동시 수집이 실제로는 1건으로 수렴하던 상태에서, 설정값대로 3건이 유지되도록 정상화.
창이 닫히지 않아 큐가 멈추는 현상도 사라졌습니다.

**이어진 작업**
엑셀 대량 소싱에서는 반대로 **너무 빨리 다음 건을 집어가는** 문제가 있었습니다.
수집 데이터가 저장되기 전에 크론이 다음 건을 픽업해, 조회 함수의 재시도 루프
(10초 간격 30회 = 최대 5분)로 버티며 워커 슬롯만 점유했습니다.
이 재시도 횟수는 큐 도입 후 지연이 늘면서 7회에서 30회로 올렸던 값이라,
증상을 재시도로 덮고 있던 상태였습니다.
크론 픽업 지점에 **저장 확인 게이트**를 넣어 상품 한 건의 사이클을 직렬화하고
(회원당 동시 3건은 유지), 무한 대기를 막기 위해 연속 실패·큐 정체 두 가지 조건으로
대기 건을 실패 처리하도록 했습니다.

## 4. 정기결제 전환 시 카드만 등록되고 청구가 누락되던 문제

**상황**
PG사 결제 클라이언트를 자동결제 전용으로 교체하면서,
월 정기결제 신규 가입자의 **카드는 등록되는데 첫 청구가 발생하지 않는** 문제.

**원인**
기존 클라이언트는 결제창에서 카드 등록과 청구를 한 번에 처리했지만,
교체한 자동결제 클라이언트는 **빌링키 발급(카드 등록)만** 수행합니다.
결제창 호출 코드가 그대로여서 등록 이후 흐름이 비어 있었습니다.

**해결**
- 월결제 경로의 결제창 요청을 **금액 0원의 순수 카드 등록**으로 명시 변경
  (일반 결제 경로는 기존 금액 청구 유지)
- 결제 통지 핸들러에서 빌링키가 포함된 통지를 카드 등록으로 판별해,
  같은 클라이언트로 **자동결제 청구 API를 호출한 뒤** 그 결과를 통지 객체에 반영.
  이후 금액 검증·주문 완료·자동결제 등록·환불 로직은 기존 일괄결제와 동일하게 동작
- **멱등 처리**: 이미 완료된 주문이거나 해당 주문에 성공 결제 이력이 있으면 재청구하지 않음

**결과**
테스트 서버에서 카드 등록 → 청구 → 주문 완료 → 기존 플랜 환불까지 전 구간 검증 후 반영.
청구 누락과 중복 청구를 모두 막았습니다.

**되짚어보면**
PG 교체는 "설정 값만 바꾸면 되는 작업"처럼 보였지만
실제로는 **결제 흐름의 단계 수가 달라지는 변경**이었습니다.
외부 연동은 응답 스펙보다 "이 API가 어디까지 책임지는가"를 먼저 확인하게 됐습니다.

## 5. 확장 연동 방식 표준화 (하드코딩 제거)

**상황**
페이지에서 크롬 확장 설치 여부를 감지하는 코드가 **운영 확장 ID를 하드코딩**하고 있었습니다.
그 결과 로컬 빌드 확장을 쓰는 개발/테스트 환경에서는 감지가 실패해
기능이 통째로 스킵되고, 문제를 인지하지 못한 채 넘어가는 일이 있었습니다.

**해결**
확장 ID에 의존하지 않는 **브릿지 + postMessage 규약**으로 통일:
- 페이지 → `postMessage({source, reqId, action, param})`
- 브릿지(content script) → 응답 `{source, reqId, action, ...결과}`
- 설치 감지는 `ping` 액션 (응답에 확장 버전·ID 포함)
- 기능 호출은 브릿지의 액션 맵에 등록하면 백그라운드로 위임
- **모르는 액션은 즉시 "지원하지 않는 요청" 으로 회신** → 구버전 확장에서도
  타임아웃 대기 없이 즉시 열화 처리 (응답 시간 635ms 확인)

**결과**
확장 ID 하드코딩과 이미지 프로브 방식의 감지를 제거했고,
신규 확장 연동 기능은 액션 하나를 추가하는 것으로 붙일 수 있게 됐습니다.
확장 스토어 배포 전까지는 해당 기능이 안전하게 열화 동작합니다.

## 개인 프로젝트

### sourcing-pipeline — https://github.com/JaeHyeokSim/sourcing-pipeline

`Java 21` `Spring Boot 4.1` `Spring Data JPA` `Flyway` `PostgreSQL` `Chrome Extension MV3` `JUnit 5`

위 실무 경험에서 반복해 마주친 문제들을 **Spring 기반으로 처음부터 재설계**한 프로젝트.
회사 코드를 옮기지 않고 문제 정의부터 다시 시작했습니다.

- 브라우저가 수집을 수행하고 **서버가 큐와 동시성 상한을 통제** (확장이 여러 개 떠도 상한 유지)
- **lease 기반 점유 + 만료분 자동 회수** — 워커가 죽어도 작업이 영원히 진행 중으로 남지 않음
- 일시 실패는 지수 백오프 재시도, 구조 오류는 즉시 확정 실패로 분리
- `(사이트, 상품ID)` 유니크 + upsert 로 재수집 멱등, 원본 페이로드 보존으로 재처리 가능
- `SiteAdapter` 구현체 추가만으로 신규 사이트 지원
- 마켓 등록은 **규칙(상품명 길이·옵션 수·금지 표현·최소가)을 전송 전에 검사**해,
  다시 보내도 소용없는 요청은 마켓 API 왕복 없이 확정 실패로 끝냄
- 마켓 호출은 트랜잭션 밖에서 수행 (준비·커밋 → 호출 → 결과 반영)
- 페이로드 해시가 직전과 같으면 재전송 요청이 와도 마켓을 호출하지 않음 (중복 등록 방지)
- 마켓이 성공 응답에 상품ID를 비워 보내면 성공으로 기록하지 않음
- 수집·등록 현황을 한 화면에서 보는 대시보드 (상태별 건수, 실패 사유, 정체 작업)
- 스키마는 Flyway 로 관리하고 **개발 H2 / 운영 PostgreSQL** 프로파일 분리.
  두 엔진에서 갈리는 타입(네이티브 enum, 라지 오브젝트)은 실제 PostgreSQL 을 띄우는 테스트로 고정

**직접 잡은 결함**
정규화 실패를 예외로 던졌더니 같은 트랜잭션에서 기록한 실패 상태가 함께 롤백되어,
작업이 진행 중으로 남아 동시 실행 슬롯을 영구 점유했습니다.
통합 테스트가 `@Transactional` 로 감싸져 있어 트랜잭션 경계가 사라진 탓에 잡히지 않았고,
실제 서버를 띄운 뒤에야 드러났습니다.
반환값(sealed interface + record) 기반으로 바꿔 상태가 반드시 커밋되게 하고,
회귀 테스트는 **일부러 트랜잭션 없이** 작성했습니다.

테스트 50건 (큐 상태 전이, 정규화 규칙, 수집 플로우, 마켓 규칙·판매가 계산,
등록 플로우, 트랜잭션 경계 회귀, PostgreSQL 스키마).
